AltPass: app map

A snapshot of the code at commit aca62da plus the later commits on main. File names and function names are the stable anchors; line numbers drift, so search for the names. Everything on this page works offline and without scripts.

What the app does, in plain language

You give AltPass a PDF. It reads the text and pictures from the file, works out the structure a sighted reader sees (title, headings, lists, tables, columns), writes it out again as clean HTML a screen reader can navigate, and then checks its own work with a scored checklist and the axe-core accessibility engine. The web page shows the before and the after side by side.

  • Reader: src/extract.js pulls text with positions, images and links out of the PDF (pdf.js).
  • Structure: src/structure.js guesses headings, lists, tables and reading order from layout.
  • Describer: src/alt/ drafts alt text (rule-based by default; optional vision-model adapters).
  • Writer: src/render.js produces the accessible HTML.
  • Checker: src/audit.js and src/axe.js score before and after and run axe-core.
  • Shop window: src/server.js (API) and public/ (the page you see).

One action, end to end

Action: click Council agenda on the home page.

Visible result: the verdict card with the score (for the council agenda, 10 to 94), the PDF pages beside the accessible preview, the live axe line, the checklist, and the alt-text review list.

A route through the code (reference route, not a toured activity)

  1. Entry point. public/app.js, search submitSample and run(. The click becomes a fetch to the API and moves the progress stepper.
    See the idea
    function submitSample(id, label) { run(label, () => fetch(`/api/samples/${id}`, { method: 'POST', ... })); }
  2. The pipeline. src/server.js, search app.post('/api/samples/:id'; then src/pipeline.js, processPdf. It calls extractPdf (src/extract.js), inferStructure (src/structure.js), fillAltText (src/alt/index.js), then renderAndAudit.
  3. The proof. src/audit.js, buildAudit and score (weights: pass 1, warn 0.6, fail 0, not-applicable excluded). src/axe.js, runAxe runs axe-core in jsdom. In the browser, public/axe-runner.js runs the same engine, including colour contrast.

To change this, start here

  • How headings, lists or tables are detected: src/structure.js (regionToBlocks, mergeTableRows, assignHeadingLevels). Add a fixture PDF under test/fixtures/ and a case in test/real-producers.test.js first.
  • Which checks and weights are scored: src/audit.js.
  • Plug in a different vision model: add a file like src/alt/openai.js and register it in selectAdapter in src/alt/index.js.
  • How the output document looks: src/render.js (renderHtml and its embedded CSS).
  • The app's look: public/styles.css (design tokens at the top) and public/index.html.
  • The demo video script: demo/record.js (captions and timings).

A practice to reuse

Decision. The plan said the output must be provably accessible, not just claimed to be (scope.md, "The Unique Kernel"; spec.md, "Auditor").

Evidence. That one sentence became checks: test/pipeline.test.js asserts zero axe violations for every sample, and test/ui.test.js runs axe on the app's own pages. The browser run found a real contrast failure in the app's own "not applicable" rows that the server-side run could not see (jsdom has no colour contrast). It was fixed and the test now guards it.

Reuse. Turn a promise in the plan into an observable check before you build the feature, and run the check in the environment where the promise matters (here, a real browser), not only in the convenient one. The same habit works for any "it should be fast / safe / accessible" claim.
